# 업무 API 요청 제한

> 후속: 운영자 모집 생성/취소도 동일 계정별 한도와 성공 멱등 키 범위를 공유한다. [운영자 구현](OPERATOR-COHORTS.md) 참고. 아래 네 기능 설명은 최초 적용 범위다.


2026-10-05 구현·로컬 검증 완료. 대상은 코호트 참여·취소·인증 작성·면제권 사용이다.

## 정책

| 구분 | 계정별 한도 | 포함하는 요청 |
|---|---|---|
| 새 업무 요청 | 60초당 20회, 3,600초당 120회 | 성공, 업무 규칙 거부, 없는 대상, 멱등 키 충돌 |
| 성공 결과 재조회 | 별도 60초당 60회 | 같은 계정·멱등 키·정규화된 내용으로 저장된 성공 응답 재조회 |

네 기능과 모든 세션·서버 인스턴스가 계정별 한도를 공유한다. 각 창은 첫 요청부터 시작하고 만료 후 첫 요청에서 초기화한다. 차단 요청은 기간을 연장하지 않는다. 이 숫자는 초기 운영값이며 실제 트래픽에 따른 조정은 후속이다.

한도 초과 응답은 HTTP 429, `RATE_LIMITED`, 초 단위 `Retry-After`, `Cache-Control: no-store`다. 요청은 업무 상태·성공 응답·감사를 추가하지 않는다. 기존 화면은 입력과 원래 멱등 키를 보관하고 대기 후 사용자가 같은 요청을 다시 확인하게 한다. 자동 쓰기 재시도는 없다.

## 구현과 경계

- `sixtysix-v2/server/business-limits.ts`에서 기존 PostgreSQL `reserveLimits`를 재사용한다. 제한 확인은 검증된 계정 세션/계정 잠금 뒤, 업무 대상 조회·코호트 잠금·쓰기 전에 수행한다.
- 저장된 성공 응답과 요청 해시가 일치할 때만 재조회 한도를 사용한다. 새 요청 한도가 소진돼도 정상 재조회는 가능하고 재조회 자체의 폭주도 제한한다.
- 업무 거부를 정상 transaction 결과로 반환하므로 한도는 누적된다. DB·감사 등 예상하지 못한 내부 오류는 업무 변경과 카운터를 함께 rollback한다. 제한 실패는 해당 transaction의 일부 카운터 증가도 rollback한다.
- 기존 `auth_rate_limits` 테이블은 업무 카운터도 담는다. 업무 전용 namespace와 무작위 계정 UUID로 키를 만들며 이메일·IP·세션 토큰을 저장하지 않는다. namespace 문자열은 비밀키나 개인정보 익명화 보장이 아니다.
- 계정별 카운터는 최대 3개다. 기존 migration 006의 만료 카운터 정리에 그대로 포함된다. 신규 migration·환경변수·런타임 권한은 없다.
- 세션 무효·CSRF·요청 schema 오류는 업무 한도를 만들지 않는다. 공개 조회, 잘못된 요청, 다수 신규 계정에 대한 네트워크/엣지 차단은 이번 계정별 업무 제한의 범위 밖이다.

## 검증

- 제한된 런타임 계정으로 PostgreSQL·HTTP **109개** 통과. 동시 요청 28개 중 정확히 20개 처리/8개 제한, 기능·세션 간 공유, 다른 계정 격리, 재조회·충돌 구분, 분/시간 창 복구, 오류 rollback, 네 route의 429·헤더·무변경을 확인했다.
- Vitest **240개 / 23개 파일** 통과. 모집과 활동 화면에서 429 후 입력/멱등 키 유지, 대기 중 버튼 제한, 수동 재시도 동일 요청을 추가 검증했다.
- 프런트·서버 타입 검사·빌드 및 OpenAPI **14개 계약 검증** 통과.
- 분당 한도를 20에서 200으로 바꾼 변이는 DB·HTTP 테스트 4개가 감지했다. 정책을 복원한 뒤 전체 DB 검증을 다시 실행했다.
- 원격 DB·환경변수·앱 배포·Production·commit/push는 변경하지 않았다. 배포된 앱에 적용하려면 후속 배포가 필요하다.
