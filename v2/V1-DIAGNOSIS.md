# 육십육 V1 진단 자료

> 용도: `beginner-mvp-v2.html` 01단계 「V1 결과물 준비」 · 02단계 「ChatGPT와 V1 진단」 입력 자료
> 작성일: 2026-09-09
> V1 배포: https://sixtysix-taupe.vercel.app
> 저장소: https://github.com/jaejinu/sixtysix

이 문서는 **V1을 만든 사람의 자기 진단**이다. 02단계에서 ChatGPT와 검토할 때 "직접 사용하며 아쉬웠던 점" 자료로 그대로 전달한다.
아래 항목은 **결론이 아니라 논의 재료**다. V2 범위는 ChatGPT와 하나씩 의논해 정한다.

## 0. V1이 무엇을 만들었는가

같은 날 시작한 30명 코호트와 하나의 습관을 66일 동안 매일 인증하고 완주하는 습관 챌린지 커뮤니티. 12화면, 사용자 상태 6개, 정책 10개를 구현했다. 프레임워크 없이 HTML·CSS·JavaScript로 만들었고 Playwright 회귀 테스트 156건이 360·390·430px에서 통과한다.

### 검증하려 했던 핵심 가설

| # | 가설 | V1 상태 |
|---:|---|---|
| 1 | 코호트 소속감이 개인 스트릭보다 완주율에 크게 작용한다 | **검증 불가** — 코호트가 정적이라 소속감이 발생하지 않음 |
| 2 | 복귀 규칙이 명확하면 이탈이 줄어든다 | **검증 불가** — 시나리오만 구현됨. 실제 이탈·복귀를 겪을 수 없음 |
| 3 | 면제권은 사용자가 직접 써야 한다 | **인터랙션 구현 완료, 가설 검증은 안 됨** |
| 4 | 랭킹은 순위보다 완주 페이스로 보여야 한다 | **표현 방식 구현 완료, 가설 검증은 안 됨** |

가설 3과 4는 처음에 "가능"으로 분류했으나 정정한다. 두 가설은 모두 **비교 명제**다.
"자동 소진보다 직접 쓰는 방식이 낫다", "순위 중심보다 완주 페이스 중심이 이 서비스에 맞다"를 확인하려면
대안과 비교하거나 사용자에게 상황을 주고 이해도·통제감·선호도를 물어야 한다.
V1에서 확인된 것은 **그렇게 동작하도록 만들 수 있다**까지다.

포트폴리오에서도 "가설을 검증했다"가 아니라
**"검증 가능한 프로토타입으로 전환했다 → 사용자 테스트로 무엇을 보았다"** 가 정확한 서술이다.

**가설 1이 서비스의 존재 이유인데 V1로는 확인할 수 없다.** 이것이 V1의 가장 큰 한계다.

## 1. 직접 써보며 가장 이상했던 것 (우선순위 순)

### P1-A. 인증을 남겼는데 피드에 내 글이 없다

**현재 문제**
인증 작성에서 공개 범위를 "코호트에 공개"로 선택하고 제출해도, 코호트 피드에 내 인증이 나타나지 않는다. 피드는 가상 멤버 6명의 고정 인증만 보여준다.

**왜 문제인가**
사용자에게 명시적으로 "우리 코호트 30명이 볼 수 있어요"라고 약속해 놓고 지키지 않는다. **기능이 거짓말을 하고 있다.** 인증 → 피드 반영은 서비스의 핵심 루프인데 그 고리가 끊겨 있다. 홈·기록·랭킹은 갱신되는데 피드만 빠져서 더 어색하다.

**원인**
내 인증(`myCheckins()`)과 코호트 인증(`FEED_CHECKINS`)이 별도 자료구조로 분리돼 있고, 피드 렌더링이 후자만 읽는다.

**개선 방향**
두 목록을 하나의 인증 스트림으로 합치고, 공개 범위가 `코호트에 공개`인 내 인증을 피드 최상단에 시간순으로 넣는다. `나만 보기`면 제외한다.

**적용 화면** 코호트 피드, 인증 상세, 홈 스토리 레일

---

### P1-B. 시간이 흐르지 않는다

**현재 문제**
기준일이 `2026-09-08`로 고정돼 있다. 내일 열어도 D+23이고, 어제 인증했든 안 했든 상태가 그대로다. 인증 마감 04:00 정책이 문서와 화면에는 설명돼 있지만 판정 로직이 없다. "늦은 인증"은 샘플 데이터로만 존재하고, 실제로 새벽에 인증해도 늦은 인증으로 기록되지 않는다.

**왜 문제인가**
66일 습관 서비스에서 **날짜가 흐르지 않으면 습관이 성립하지 않는다.** 스트릭이 끊기는 경험, 어제를 놓친 아쉬움, 오늘 마감 전에 서두르는 긴장 — 이 서비스를 지탱하는 감정이 전부 시간에서 나오는데 그게 없다.

**개선 방향**
실제 날짜 기준으로 D+N을 계산하고, 마지막 인증일과 오늘을 비교해 연속·끊김·휴면을 판정한다. 04:00 마감과 12시간 지각 창구를 실제 시각으로 판정한다. 데모용 날짜 이동 수단은 별도로 유지한다.

**적용 화면** 전 화면 (특히 홈, 인증 작성, 기록)

---

### P1-C. 코호트가 살아 있지 않다

**현재 문제**
멤버 8명이 고정값이고, "30명 중 18명 인증"의 18은 하드코딩이다. 내가 인증하면 19가 되지만 그뿐이다. 내가 남긴 인증에는 아무도 응원하지 않는다. 어제도 오늘도 같은 6개의 인증이 피드에 있다.

**왜 문제인가**
가설 1을 검증할 수 없게 만드는 직접적인 원인이다. "같이 하고 있다"는 느낌은 **다른 사람이 나와 상관없이 움직일 때** 생기는데, 지금은 배경 그림에 가깝다. 30명 코호트라면서 8명만 존재하는 것도 숫자가 겉돈다.

**개선 방향**
멤버를 30명으로 채우고 각자 인증 이력을 갖게 한다. 날짜가 바뀌면 그날의 인증이 새로 생기게 하고, 내 인증에 시간차를 두고 응원이 붙게 한다. 서버 없이 결정론적 생성으로 처리 가능하다.

**적용 화면** 홈 코호트 현황, 코호트 피드, 코호트 랭킹, 챌린지 상세

---

### P2-D. 온보딩 직후의 상태가 앞뒤가 안 맞는다

**현재 문제**
온보딩에서 습관을 처음 고르고 나면 곧바로 D+23, 채운 날 21일 상태로 시작한다. 첫 사용자인데 3주치 기록이 이미 있다.

**왜 문제인가**
데모에서 66칸이 3분의 1 차 있는 그림을 보여주려는 의도였는데, 온보딩 흐름과 정면으로 충돌한다. V1에서는 안내 문구로 얼버무렸다("데모는 23일차부터 시작해요"). 문구로 덮은 것이지 해결한 것이 아니다.

**개선 방향**
온보딩을 마치면 0일차에서 시작하고, 진행 중인 상태는 데모 전환으로만 진입하게 한다. 또는 온보딩 마지막에 "처음부터 시작 / 진행 중인 상태로 둘러보기"를 명시적으로 고르게 한다.

**적용 화면** 온보딩, 홈

---

### P2-E. 인증 사진이 5장 돌려쓰기다

**현재 문제**
인증 작성에서 미리 준비된 샘플 사진 5장 중 하나를 고른다. 66일이면 같은 사진이 13번씩 반복된다.

**왜 문제인가**
인증의 진정성이 이 서비스의 재료인데, 며칠만 써봐도 피드가 똑같아 보인다. 기록을 돌아보는 재미도 사라진다.

**개선 방향**
기기의 실제 사진을 선택하게 한다. 파일 선택 + 로컬 미리보기는 서버 없이 가능하고, `localStorage` 대신 IndexedDB에 저장하면 용량도 감당된다. MVP 제외 항목이었지만 **투입 대비 효과가 가장 좋은 후보**다.

**적용 화면** 오늘 인증 작성, 피드, 기록

---

### P2-F. 66칸을 눌러볼 수 없다

**현재 문제**
66칸 진행판이 표시 전용이다. 34px 타일이 44px 터치 기준에 미달해서 클릭 대상에서 제외했다.

**왜 문제인가**
기록을 되짚는 것이 이 화면의 목적인데, 정작 "그날 뭐 했더라"를 확인하는 가장 자연스러운 동작이 막혀 있다. 접근성 기준을 지킨 결과가 기능을 없애는 쪽으로 갔다.

**개선 방향**
11열 표시 뷰와 6열 상세 뷰를 전환하게 한다. 6열이면 타일이 약 59px이라 터치 기준을 만족하면서 날짜별 진입이 가능하다. 또는 진행판 아래 날짜 목록과 진행판을 양방향으로 연동한다.

**적용 화면** 기록

---

### P3-G. 밀도가 낮은 화면 3개

| 화면 | 현재 | 문제 |
|---|---|---|
| 공지 | 공지 3건, 펼치기/접기만 | 화면 하나를 차지할 분량이 아님. 홈 배너로 충분할 수 있음 |
| 코호트 랭킹 | 9명 목록 | 30명 코호트라면서 9명만 보임. 숫자가 겉돎 |
| 졸업(완주) | 미리보기 진입 시 수치가 하드코딩 | 내 실제 기록과 무관한 값이 보임 |

**왜 문제인가**
화면 수를 유지하려고 만든 화면이 있다는 인상을 준다. 12화면이라는 숫자보다 각 화면이 존재할 이유가 중요하다.

**개선 방향**
공지는 홈 섹션이나 마이 하위로 흡수하는 안을 검토한다. 랭킹은 30명을 다 채우고 접기/더보기를 둔다. 졸업은 실제 기록에서 계산한다.

---

### P3-H. 탐색의 진입점이 세 군데다

**현재 문제**
하단 탭 4개(홈·피드·기록·마이)에 챌린지 탐색이 없어서, 홈 헤더 아이콘·홈 섹션 전체 보기·졸업 CTA 세 곳에 진입점을 따로 만들었다.

**왜 문제인가**
진입점을 여러 개 만들어야 했다는 것 자체가 **정보 구조가 자연스럽지 않다는 신호**다. 다만 한 코호트에 66일 머무는 서비스에서 탐색은 시작·졸업 시점에만 쓰이므로 상시 탭을 줄 대상도 아니다. 재검토가 필요한 지점이다.

**개선 방향**
탐색을 코호트 종료 시점에만 노출되는 화면으로 재정의하거나, 마이 하위로 옮기는 안을 검토한다.

## 2. 유지해야 할 것 (V2에서 건드리지 말 것)

제작 과정에서 판단 근거를 남겨 둔 결정들이다. 바꿀 이유가 생기기 전까지 유지한다.

| 항목 | 근거 |
|---|---|
| 66칸 진행판이 키 비주얼이라는 것 | 서비스를 한 장으로 설명하는 요소. 코랄이 채워지는 그림 |
| 상태를 색상만으로 구분하지 않는 원칙 | 진행판 6상태를 채움·점·사선·테두리로 구분. 배지는 아이콘+라벨 병기 |
| 대표 컬러 위 검정 텍스트 | 코랄 위 흰 텍스트는 3.6:1로 기준 미달. 검정은 4.8:1 |
| 코랄 텍스트용 어두운 변형 `#C63A1E` | 코랄 원색은 배경 대비 3.4:1로 텍스트 사용 불가 |
| 액센트 그린을 완료·복귀에만 쓰는 제한 | 장식으로 번지면 상태 의미가 희석됨 |
| 정책을 규칙 문장으로 노출하지 않는 문구 원칙 | "미인증 시 스트릭 리셋" → "어제는 쉬었어요. 오늘 인증하면 다시 이어져요." |
| 사진 없는 인증에 다른 사진을 채우지 않는 원칙 | 간단 인증은 남긴 한 줄을 그대로 보여줌 |
| 앱 셸 430px · 콘텐츠 394px · 여백 18px | 기준 문서 규격 |
| 하단 고정 UI 중복 금지 | BottomNav와 StickyActionBar 동시 노출 안 함 |

## 3.5 Figma 이전(03단계) 중 발견한 문제 (2026-09-10)

V1.1 을 Figma 로 옮기면서 실제 화면을 확대해 보니 드러난 것이다.
**V1 에서 고치지 않는다.** 동결 원칙을 지키고 V2 과제로 넘긴다.

### 사진 위 텍스트 대비가 부족하다

Hero 의 Scrim 은 `linear-gradient(to top, 0.72 → 0.42(45%) → 0)` 로 하단만 어둡다.
그런데 텍스트 블록은 카드 높이의 절반 지점(y≈213)부터 시작한다.
그 위치의 Scrim 농도는 **약 0.15** 에 불과하다.

`hero-morning-desk` 는 창가 역광 사진이라 그 구간이 가장 밝다. 결과적으로

- `D+23` 코랄(`#F04E2C`)이 밝은 나무 바닥 위에 놓여 거의 묻힌다
- `오늘 인증만 남았어요` 흰 텍스트도 대비가 약하다

디자인 규정 13.2 는 *"텍스트 그림자만으로 대비 문제를 해결하지 않는다"*,
*"슬라이드마다 이미지가 달라지는 경우 각 이미지에서 대비를 확인한다"* 라고 적어 두었는데
**규정을 만들어 놓고 실제 이미지가 들어온 뒤 확인하지 않았다.**
이미지 없이 개발하고 마지막에 넣었기 때문이다.

**개선 방향(V2)**: Scrim 을 텍스트 블록 높이에 맞춰 올리거나,
텍스트 영역만 별도 면으로 분리한다. 대표 컬러를 사진 위 텍스트로 쓰는 것 자체를 재검토한다.
`#F04E2C` 는 배경 대비 3.4:1 이라 원래 텍스트용이 아니다.

### 한 줄 카운터가 실제 입력과 무관한 숫자를 보여준다

인증 작성 화면의 `한 줄 남기기` 입력은 `maxlength="60"` 인데,
입력이 **0자인 상태에서 카운터가 `40`** 으로 표시된다.
남은 글자 수라면 `60`, 입력 글자 수라면 `0` 이어야 한다. 둘 중 어느 쪽도 아니다.

Playwright 210건이 못 잡은 이유는 3.4 와 같다.
카운터가 **존재하는지**만 보고 **값이 입력과 일치하는지**는 보지 않았다.
표시 전용 테스트의 한계가 같은 방식으로 한 번 더 드러난 사례다.

**개선 방향(V2)**: 카운터를 입력 길이에서 파생시키고(`60 - value.length`),
`stored facts vs derived values` 원칙대로 별도 상태로 두지 않는다.
테스트는 "값을 넣으면 카운터가 따라 변한다"를 검사한다.

### 이 발견들의 의미

두 건은 성격이 다르고, 각각 다른 교훈을 남긴다.

**대비 문제**는 V1 진단 8건에 없던 **시각 품질** 문제다.
이미지가 실제로 들어온 뒤에야 보이는 종류이므로,
**V2 에서는 이미지를 먼저 넣고 화면을 만든다**.

**카운터 문제**는 3.4 와 같은 계열, 즉 **표시와 데이터의 불일치**다.
3.4 에서 상태 정합성 테스트 층(`state.spec.js`)을 만들었는데도 이건 남아 있었다.
그 층이 **저장 상태**만 검사하고 **화면 안에서 파생되는 값**은 검사하지 않았기 때문이다.
V2 의 검사 대상은 세 층이 된다 — 표시 / 저장 상태 / 파생 값.

**공통점**: 둘 다 "화면을 한 번 더 천천히 본" 결과 나왔다.
Figma 이전은 옮기는 작업인 동시에 **정밀 검수 과정**이기도 했다.

## 5. V2 구현 관점 메모

V2가 React·TypeScript 재구현이므로 옮길 때 참고할 사항이다.

**옮기기 쉬운 부분**
`derived()`가 인증 목록에서 스트릭·채운 날·상태를 계산하는 순수 함수라 그대로 훅으로 전환 가능하다. 데이터·상태·렌더링·라우팅이 파일로 분리돼 있다.

**다시 설계해야 하는 부분**
`render()`가 화면 전체를 문자열로 다시 그리는 방식이라 입력 포커스가 유실되고, 탐색 검색창에서 이를 수동으로 복원하고 있다. React로 가면 이 문제는 사라지지만 그 대신 컴포넌트 분해가 필요하다. 전역 `ACTIONS` 객체에 모든 이벤트가 모여 있어 컴포넌트 단위로 나눠야 한다.

**유지할 자산**
디자인 토큰 CSS는 그대로 쓸 수 있다. Playwright 테스트 156건은 셀렉터 기준이라 마크업 구조를 유지하면 상당수 재사용 가능하다. 생성 이미지 10장과 문구는 전부 유지.

## 6. 논의가 필요한 열린 질문

02단계에서 ChatGPT와 결론을 내야 할 항목이다.

1. **가설 1(코호트 소속감)을 V2에서 검증 가능하게 만들 것인가?** 만든다면 코호트를 동적으로 살리는 작업이 V2의 중심이 된다. 안 만든다면 V2는 UI 고도화에 그친다.
2. **시간을 실제로 흐르게 할 것인가?** 흐르게 하면 데모로 보여주기 어려워진다(하루에 한 번만 인증 가능). 데모 편의와 서비스 진정성 사이의 선택이다.
3. **화면 12개를 유지할 것인가?** 밀도가 낮은 3개를 정리하면 10개가 된다. 화면 수 유지가 목적이 되면 안 된다.
4. **실제 사진 업로드를 넣을 것인가?** 효과는 크지만 MVP 제외 항목이었고 저장소 설계(IndexedDB)가 따라온다.
5. **탐색을 어디에 둘 것인가?** 진입점 3개는 구조가 어색하다는 신호다.
