## 결정 1 — V2의 중심 (확정)

**가설 1(코호트 소속감이 개인 스트릭보다 완주율에 크게 작용한다)을 검증 가능한 프로토타입으로 만드는 것.**

V2가 증명하는 것과 증명하지 않는 것을 구분한다.

| | |
|---|---|
| V2가 만드는 것 | 정적인 코호트 → **살아 있는 코호트 경험** → 사용자 테스트가 가능한 프로토타입 |
| V2가 증명하지 **못하는** 것 | "코호트가 실제 66일 완주율을 높였다". 실사용자 66일 관찰이나 실서비스 데이터가 필요하다 |

포트폴리오 서술도 "가설을 검증했다"가 아니라 **"검증 가능한 프로토타입으로 전환했다 → 사용자 테스트로 무엇을 보았다"** 로 쓴다.

### 가설별 현재 상태 (재분류)

| # | 가설 | V1 상태 | V2 목표 |
|---:|---|---|---|
| 1 | 코호트 소속감 | 검증 불가 | **검증 가능하게 만든다 (V2의 중심)** |
| 2 | 복귀 규칙 | 검증 불가, 시나리오만 구현 | 시간·코호트가 살아나면 함께 검증 가능해짐 |
| 3 | 면제권 직접 사용 | 인터랙션 구현 완료, 가설 검증 안 됨 | 사용자 테스트 대상 |
| 4 | 완주 페이스 중심 랭킹 | 표현 방식 구현 완료, 가설 검증 안 됨 | 사용자 테스트 대상 |

가설 3·4는 **비교 명제**다. 구현했다는 것과 그 방식이 더 낫다는 것은 별개다.

## 결정 2 — V1 처리 (완료 후 동결)

포트폴리오 링크로 노출 중이므로 **정합성·공정성 버그 3건만** 선행 수정하고 더 이상 기능을 추가하지 않는다.

| 문제 | V1.1 | V2 |
|---|---|---|
| 온보딩 습관·코호트 불일치 | ✅ 수정 | 통합 `Cohort` 모델로 재설계 |
| 코호트 참여가 상태를 안 바꿈 | ✅ 수정 (예약으로 정리) | `Membership` 모델로 재설계 |
| 면제권 때문에 내 랭킹만 유리 | ✅ 수정 | 랭킹 selector 재작성 |
| 내 인증이 피드에 없음 | ❌ 건드리지 않음 | 통합 `Checkin` 모델에서 해결 |
| 시간이 흐르지 않음 | ❌ 건드리지 않음 | `Clock` 모델에서 해결 |
| 8명뿐인 정적 코호트 | ❌ 건드리지 않음 | 30명 `Simulator` 에서 해결 |

**이 경계를 지킨다.** 시간·시뮬레이터·통합 모델을 V1에 넣기 시작하면 V2를 두 번 만드는 셈이 된다.

### V1.1에서 실제로 한 일

**버그 3건**

1. 진행 중 코호트를 습관마다 하나씩 두고(`c-<습관>-0817`) 선택 습관의 코호트를 배정한다. 온보딩이 습관명을 문자열로 조합해 보여주던 것을 없애고 실제 배정 코호트명을 표시한다.
2. 정책 7(한 번에 한 코호트)에 따라 진행 중이면 **참여가 아니라 예약**으로 처리하고 `nextCohortId`에 저장한다. 완주 후에만 실제 배정한다. 이미 시작한 코호트는 참여 불가 처리하고 탐색 목록에서 제외한다.
3. 랭킹을 `filled`(면제권 포함)가 아니라 `checkins`(실제 인증)로 계산한다. 모든 멤버가 같은 기준을 쓴다.

**개념 분리 확정**

```
채운 날 (filled)   = 인증 + 면제권   → 66일 완주 페이스
인증 수 (checkins) = 실제 인증만     → 랭킹
면제권  (passes)                     → 연속성 보호 장치
```

면제권은 순위를 올려주는 쿠폰이 아니라 **연속성을 지키는 장치**다.

**곁가지 수정**

마이 화면 습관명 중복 · 코호트명 규칙 통일(`영어 단어 20개 · N기`) · 예약 Toast 목적격 조사 · 예약한 코호트를 마이 화면에 노출(저장만 되고 보이지 않으면 상태가 없는 것과 같다)

**회귀 테스트**

기존 156건이 전부 "화면에 무엇이 보이는가"만 검사해 세 버그를 하나도 잡지 못했다. `qa/tests/state.spec.js`로 **저장 상태 정합성** 층을 신설했다.

| 검사 | 내용 |
|---|---|
| 온보딩 정합성 | 습관 6종 각각 배정 코호트의 `habitId` 일치, 코호트명이 습관명으로 시작, 마이 화면 표시 일치 |
| 랭킹 공정성 | 인증 20 + 면제권 1 → 채운 날 21이어도 랭킹 계산값은 20 |
| 예약 지속성 | 예약 후 새로고침·재진입에도 유지, 활성 코호트는 불변, 마이에서 다시 찾을 수 있음 |
| 인증 저장 | 공개 범위·간단 인증이 저장 상태에 반영 |

**156건 → 210건**, 360·390·430px 전부 통과.

V1은 **v1.1**로 잠근다. 이후 기능을 추가하지 않는다. 배포: https://sixtysix-taupe.vercel.app

## 결정 3 — V2 구현 순서 (3 Gates)

작업 순서가 아니라 **게이트**다. 앞 게이트의 데이터 계약과 테스트가 통과해야 다음으로 간다.

### Gate 1. Domain / Data Model

세계의 법칙을 먼저 정한다.

```
User · Habit · Cohort · Membership · Checkin · PassUsage · Reaction · Badge
```

특히 지금 흩어진 것을 `Checkin` 하나로 통합한다.

```
days · texts · photoDays · simpleDays · privateDays · FEED_CHECKINS
        ↓
Checkin { id, memberId, cohortId, day, createdAt, effectiveDate,
          text, photo, scope, status: normal|late|return, cheers }
```

**상태: 완료 (2026-09-09)** — `sixtysix-v2/` 에 구현. 불변식 16개 + baseline acceptance 32개 테스트 통과.

**통과 기준** — UI 완성도가 아니다.

> Checkin 목록 하나를 주면 스트릭·인증 수·채운 날·상태·랭킹을 모두 계산할 수 있는가?

이게 되면 P1-A(내 인증이 피드에 없음)가 구조적으로 사라진다. 피드와 기록이 별개 데이터가 아니라 **같은 Checkin에 다른 렌즈를 씌운 결과**가 되기 때문이다.

이 게이트가 끝나기 전에는 Simulator로 가지 않는다.

### Gate 2. Cohort Simulator

30명의 행동을 만든다. 각 멤버가 날짜별로 인증했는지, 늦었는지, 빠졌는지, 휴면인지, 복귀했는지, 누구를 응원했는지를 갖는다.

**진행 상황 (2026-09-09)** — 1~3단계 완료, 4~5단계 진행 중

```
✅ 1. Random primitive 고정        valueFor() + seed 계약, 방화벽 16개
✅ 2. 원형 파라미터 스키마 고정      ArchetypeParams 8개 축
✅ 3. 6종 원형 수치 설정            steady·ordinary·deadline·hotStart·comeback·atRisk
✅ 4. 경로 의존 상태 전이 구현       stepMember + getAttendanceProbability
✅ 5. 30명 구성과 66일 시뮬레이션    날짜 우선 루프, 배분 확정, 29명 + 사용자 1명
✅ 6. 분포·궤적 검증 후 튜닝        기준 세계에 실제 이탈이 생기도록 재조정
✅ 7. cohortMomentum A/B           복귀 특화, 계수 0 → 0.35
```

**A/B 결과 (같은 seed, 계수만 변경)**

| 지표 | 계수 0 | 계수 0.35 |
|---|---:|---:|
| 3일 내 복귀율 | 81.6% | **86.9%** |
| 휴면 경험 인원 | 9명 | **7명** |
| 평균 채운 날 | 39.5 | **41.3** |
| steady 원형 평균 | 57.6 | 57.6 |
| stayedToEnd (보조) | 26명 | 25명 |

**이 표가 Gate 2 의 최종 기준선이다.** `src/simulator/__tests__/frozen.test.ts` 에 스냅샷으로 잠겨 있다.

> 작업 중 "복귀율 40%" 와 "62%" 가 문서에 남았는데, 중간 결과가 아니라
> **같은 이름을 서로 다르게 계산한 것**이었다. 분모가 미인증 *일수* 냐 *구간* 이냐의 차이다.
> 정의를 `src/simulator/metrics.ts` 한 곳으로 모으고 **미인증 구간의 시작**을 분모로 확정했다.
> 최종 기준선은 위 표의 81.6% 다.

**steady가 움직이지 않는 것이 메커니즘이 깨끗하다는 증거다.** 코호트 효과가
잘하고 있는 사람에게 번지지 않고 빠진 사람의 복귀에만 작용한다.

**`stayedToEnd`는 이 시뮬레이션에서 판별력이 없다.** 정의상 마지막 7일 안에
한 번만 행동해도 성립하므로 양쪽 다 86% 이상이다. 정의를 숫자에 맞춰 고치지 않고,
A/B 의 1차 지표를 복귀율과 휴면 인원으로 둔다.

이것은 **시뮬레이션 시나리오의 결과이지 가설 1을 검증한 데이터가 아니다.**
사용자 테스트를 가능하게 만드는 실험 장치다.

**순서가 중요했다.** 원형 숫자부터 잡으면 나중에 `valueFor()`의 분포나 seed 규칙을 바꿀 때
"행동 파라미터가 잘못됐나, 랜덤 기반이 바뀌었나"를 구분할 수 없다.

**세 층을 섞지 않는다.**

```
valueFor                 = 운
getAttendanceProbability = 성향 + 과거
simulateMember           = 둘을 결합
```

`simulateMember`는 판단이 아니라 **도메인 사실**(Checkin · PassUsage)을 출력한다.
`late`·`simple`·`returning`은 여기서 정하지 않고 Gate 1 셀렉터가 `createdAt`과 이력에서 파생한다.
이 구조 덕분에 시뮬레이터가 Gate 1의 불변식을 자동으로 통과해야 한다.

**원형 1명씩 66일 궤적 (중간 완료 기준)**

```
steady    인증 55 · 늦은  3 · 간단  7 · 면제 2 · 최장연속 25 · 휴면 0 · 복귀  5
ordinary  인증 41 · 늦은  6 · 간단  4 · 면제 1 · 최장연속  8 · 휴면 0 · 복귀 12
deadline  인증 44 · 늦은 20 · 간단 17 · 면제 1 · 최장연속  9 · 휴면 0 · 복귀 13
hotStart  인증 49 · 늦은  8 · 간단  6 · 면제 0 · 최장연속 14 · 휴면 0 · 복귀 12
comeback  인증 30 · 늦은  3 · 간단  8 · 면제 1 · 최장연속  8 · 휴면 1 · 복귀 14
atRisk    인증 22 · 늦은  6 · 간단  7 · 면제 0 · 최장연속  4 · 휴면 3 · 복귀  9
```

`deadline`은 출석이 나쁜 사람이 아니라 **막판에 나타나는 사람**이다(인증 44로 ordinary보다 높고 늦은 인증 20).
`steady`도 인증 55로 완벽하지 않다. 각본이 아니라 성향이어야 하기 때문이다.

### 결정 5 — 성취 지표 (확정)

생애주기와 성취를 이름부터 분리한다. `completed`를 쓰지 않는다. `ended`와 다시 섞이기 때문이다.

| 개념 | 코드 | 의미 |
|---|---|---|
| 코호트 종료 | `membershipStatus === 'ended'` | 66일 기간이 끝남 (생애주기) |
| 끝까지 함께함 | `stayedToEnd` | 마지막 7일 안에 인증 또는 면제권 사용이 있음 |
| 66칸 채움 | `filled66` | Checkin + PassUsage 로 66일을 모두 채움 |
| 완벽 인증 | `perfect66` | 실제 인증 66회, 면제권 0회 |

응원만 누른 사람은 참여로 보지 않는다. 습관 챌린지를 계속한 것이 아니기 때문이다.

**정의를 결과에 맞춰 조정하지 않는다.** 먼저 고정하고 19명이 나오든 25명이 나오든 받아들인다.

졸업 화면 문구도 바뀐다.

> ~~같이 시작한 30명 중 22명이 함께 완주했어요~~ ← V1 에서 근거 없이 적은 숫자
> **같이 시작한 30명 중 N명이 마지막 주까지 함께했어요** ← 실제 계산값

### 결정 6 — cohortMomentum은 복귀 특화 (확정)

가설 1은 "잘하는 사람을 58일에서 61일로 올린다"가 아니라
**"2~5일 빠진 사람이 코호트의 움직임을 보고 돌아온다"** 를 검증해야 한다.

```
연속 참여 중(misses === 0)      → 보정 0. 적용하지 않는다
1일 빠짐                        → 작게
2~4일 빠짐                      → 가장 크게
5~6일 빠짐                      → 여전히 크게
7일 이상(휴면)                   → 줄지만 0 은 아니다
```

신호는 **최근 3일** 참여율을 쓴다. 하루만 보면 우연에 민감하다.
**본인은 제외한다.** 내가 인증해서 내 복귀 확률이 오르는 순환을 막아야 한다.
절반(0.5)을 기준으로 비선형(제곱근)으로 편다. 절반 미만은 포기 전염, 넘으면 함께 가는 느낌이다.

A/B는 같은 seed 세계에서 계수만 바꾼다. 랜덤 세계가 달라지면 차이가 코호트 효과인지 운인지 알 수 없다.

---

**통과 기준** — 결정론.

> 같은 seed와 같은 날짜면 항상 같은 결과가 나오는가?
> 새로고침해도 도윤이 인증했다 안 했다 하지 않는가?

seed는 `(cohortId, memberId, day)` 단위로 잡는다. 렌더 시점이나 현재 시각에 의존하면 **시계를 넘길 때 과거가 바뀐다.**

여기까지 가면 코호트가 배경 사진에서 등장인물로 승격된다.

### Gate 3. Clock / Time Engine

**상태: 완료 (2026-09-10)** — 121개 테스트 통과. 4개 시간대에서 동일.


시간은 **마지막에** 넣는다. 먼저 넣으면 버그가 났을 때 데이터 문제인지 시뮬레이션 문제인지 날짜 문제인지 범인이 셋이 된다.

```
Clock
 ├─ RealClock
 └─ DemoClock
```

도메인 코드에서 `new Date()`를 직접 부르지 않고 `clock.now()`만 쓴다.

**통과 기준** — 도메인 코드에 `new Date()` 직접 호출이 0건인가.

**방화벽 6개 + 스냅샷 보존**

| # | 검사 |
|---:|---|
| 1 | RealClock 은 현재 시각을 반환하고 임의 이동할 수 없다 |
| 2 | DemoClock 은 동일 저장값에서 항상 동일한 now 를 반환한다 |
| 3 | D+23 → D+24 로 옮겨도 D+1~23 의 판정이 변하지 않는다 |
| 4 | 미래 데이터가 생성돼 있어도 selector 결과에 노출되지 않는다 |
| 5 | Demo 와 Real 의 저장 상태가 섞이지 않는다 |
| 6 | 04:00 경계와 12시간 늦은 인증 창구가 같은 now 에서 일관되다 |
| — | **Gate 2 스냅샷 보존** — Clock 을 꽂아도 시뮬레이터 결과가 한 숫자도 안 움직인다 |

**시간대를 정책에 명시했다.** 기존 `getCohortDay` 는 브라우저 로컬 시각에 기대고 있어
해외에서 열면 04:00 규칙이 어긋났다. `Policy.timeZone = 'Asia/Seoul'` 로 옮기고
`Intl.DateTimeFormat` 으로만 변환한다. Asia/Seoul · UTC · America/New_York · Pacific/Auckland
네 시간대에서 121개가 동일하게 통과한다.

**방화벽 4번이 Gate 1 의 실제 버그를 잡았다.** 시뮬레이터가 66일을 미리 만들어 두니
미래 인증이 진행판·통계·랭킹·배지에 새어 나왔다. 모든 파생 함수를 시계 인식으로 고쳤다.
Clock 이 커튼이라는 원칙이 코드로 강제된 것이다.

**Clock 은 일차를 계산하지 않는다.**

```
Clock  = 지금 몇 시인가
Policy = 이 시각이 어느 cohortDay 에 귀속되는가
```

## 결정 4 — 시간 구조 (확정)

### 4-A. Clock 정책

**최초 방문은 DemoClock이 기본이다.** RealClock이 기본이면 포트폴리오 링크를 처음 여는 사람이
0일차·빈 피드·빈 진행판을 보게 되어, 가장 보여줘야 할 "코호트가 살아 있는 상태"에 도달하지 못한다.

| 상황 | Clock | 상태 |
|---|---|---|
| 최초 방문 | DemoClock | D+23 정도의 충분히 쌓인 시점 |
| 데모 날짜 이동 | DemoClock | D+1 ~ D+66 자유 탐색 |
| 실제 시간으로 체험 | RealClock | 실제 현재 시각 기준 |
| 데모로 복귀 | DemoClock | 기존 데모 상태 복원 |

**Demo와 Real은 저장 영역을 분리한다.** 같은 Checkin 데이터를 공유하면
DemoClock에서 D+23 인증을 남긴 뒤 RealClock(D+1)으로 바꿨을 때 **미래의 인증이 이미 존재하는** 모순이 생긴다.

```
state = {
  mode: 'demo' | 'real',
  demo: { clock, userData },
  real: { clock, userData }
}
```

모드 전환은 데이터 변환이 아니라 **다른 세션으로 들어가는 것**에 가깝게 만든다.

DemoClock일 때는 화면 어딘가에 데모 시간임을 표시한다. 심사자가 D+23을 실제 데이터로 오해하지 않게 하기 위함이다.

### 4-B. Simulator 정책

기준 축을 달력 날짜가 아니라 **코호트 일차**로 잡는다. 66일 서비스의 핵심 식별자는
`2026-09-08`이 아니라 `이 코호트의 23일차`다.

```
seed(simulatorVersion, cohortId, memberId, day, dimension)
```

**`dimension`이 핵심이다.** `(cohortId, memberId, day)` 하나로 PRNG 스트림을 만들면

```js
const attended = rand()
const time     = rand()
const photo    = rand()
// 나중에 여기 const late = rand() 를 끼워 넣는 순간
// 뒤의 time·photo 결과가 전부 바뀐다 → 지난 22일의 역사가 통째로 흔들린다
```

각 축을 독립 해시로 뽑으면 `photo` 로직을 고쳐도 출석 여부는 그대로다.

```js
valueFor(cohortId, memberId, 23, 'attendance')
valueFor(cohortId, memberId, 23, 'checkinTime')
valueFor(cohortId, memberId, 23, 'photo')
```

`simulatorVersion`은 알고리즘을 의도적으로 크게 바꿀 때만 올려 데모 세계를 재생성한다.

### 4-C. Clock과 Simulator의 역할 분리

| | 답하는 질문 |
|---|---|
| Clock | **지금이 언제인가** |
| Simulator | **그 날짜까지 이 30명에게 무슨 일이 있었는가** |

```
clock.now() → getCohortDay(now, cohort) → D+23 → simulator.getMemberDay(memberId, 23)
```

**DemoClock을 하루 넘기는 것은 데이터를 새로 만드는 행위가 아니라,
이미 결정된 코호트 역사에서 다음 하루를 공개하는 행위다.**

```
D+1 ~ D+23  이미 결정됨 (변하지 않음)
D+24        새로 공개
D+25 이후    아직 미래
```

이래야 66칸 진행판이 진짜 역사 기록처럼 동작한다.

### 4-D. 보완 — 결정론만으로는 부족하다

결정론적 해시는 **랜덤의 출처**를 고정할 뿐, 그것만으로는 코호트가 사람처럼 보이지 않는다.

**① 멤버 행동은 경로 의존이어야 한다.** 매일을 독립 추첨으로 뽑으면
연속·이탈·복귀 없이 깜빡이는 점 30개가 된다. 가설 1을 검증할 수 없는 그림이다.

```
attendance(day) = f( hash(…, day, 'attendance'), state(day-1) )
```

`state(day-1)`도 결정론적이므로 전체는 여전히 결정론적이고 과거도 안정적이다.
20일 연속인 사람은 이어갈 확률이 높고, 3일 빠진 사람은 휴면으로 갈 확률이 높아야 한다.

**② 멤버에게 원형(archetype)을 준다.** V1에 이미 있다 — 도윤(성실 완주형),
수빈(늦은 인증형), 예준(이탈 후 복귀형), 민준(휴면형). V2에서는 이 성격을
시뮬레이터 파라미터로 주고 행동이 거기서 **자라나게** 한다. 라벨로 붙이지 않는다.
