# 육십육 백엔드 B0 — 권장 정책과 첫 개발 명세

> 작성·갱신: 2026-10-05
> 상태: **이메일 인증번호 + 카카오 로그인, 공개 모집 확정 / 세부 정책은 권장안 / 구현 전**
> 상위 현황: [FUNCTIONAL-BACKEND-PLAN.md](FUNCTIONAL-BACKEND-PLAN.md)
> 이 문서는 기존 확정 규칙, 이번 권장안, 구현 변경점을 구분한다. 사용자 선택 전 권장안을 승인된 제품 정책으로 취급하지 않는다.

T02 후속 산출물: [기술 구성](BACKEND-TECH-ARCHITECTURE.md) · [업무 DB migration](../backend/db/001_initial.sql) · [OpenAPI v0.2](../backend/openapi.json). 아래 API 표는 요약이며 실제 경로·필드 계약은 OpenAPI를 따른다. API 서버와 인증 연동은 아직 미구현이다.

## 1. 첫 개발의 목표

서로 다른 실제 계정 두 개가 같은 코호트에 참여하고, 인증 한 건을 저장했을 때 홈·기록·피드·순위가 같은 결과를 보여주는 흐름을 완성한다.

사용자 결정에 따라 첫 릴리스부터 **이메일 인증번호와 카카오 로그인을 모두 제공하고 공개 모집**한다. 서버·DB는 실제 계정과 사실을 사용하고 가상 멤버는 섞지 않는다. 공개 오픈 전에 내부 검수 환경에서 두 계정·동시 요청·운영 처리를 검증하되, 초대 사용자 전용 서비스로 출시 범위를 바꾸지 않는다.

첫 범위에서 미루는 것: 실제 사진 업로드, 활성 코호트 중 다음 기수 예약, 자유로운 인증 수정·삭제, 응원, 공지 CMS, 마케팅/습관 리마인더 알림, 졸업 전용 화면. 종료 요약 데이터와 기존 기록 화면 연결은 포함한다. 모집 취소·탈퇴 처리 같은 필수 운영 결과 안내는 포함한다.

## 4. 시간·상태·행동 계약

### 4.1 서로 다른 세 값

- `cohortDay`: 현재 업무 일차. 종료 뒤 67 이상이 될 수 있는 계산값.
- `displayDay`: 화면의 진행판 기준. 시작 전 0, 그 외 최대 66.
- `availability.targetDay`: 지금 접수할 일차. 쓰기 가능할 때만 1~66.

종료 표시만 보고 인증을 막지 않는다. `availability.ok`를 먼저 확인한다. 일정 종료와 최종 접수 종료를 분리한다.

### 4.2 경계 판정

예시: 시작 2026-08-17, 66일차 2026-10-21, 모두 KST. 서버가 트랜잭션 내에서 판정 시각을 한 번 정해 사용한다.

| 시각·조건 | 접수 결과 | 홈 행동 |
|---|---|---|
| 8/17 03:59:59 | BEFORE_START | 시작 대기 |
| 8/17 04:00, 1일차 비어 있음 | 1일차 정상 | 첫 인증 |
| 일반일 03:59:59 | 전날 정상 창 | 대상 날짜의 인증 |
| 일반일 04:00, 어제가 비어 있음 | 어제 늦은 인증 | ‘어제 늦은 인증’ |
| 일반일 16:00:00.000, 어제가 비어 있음 | 어제 늦은 인증 허용 | 같은 대상 유지 |
| 일반일 16:00:00.001 | 오늘 정상 창 | 대상 변경이면 확인 후 재접수 |
| 어제를 이미 채웠음 | 오늘 비어 있으면 오늘 정상 창 | 오늘 인증 |
| 10/22 03:59:59, 66일차 비어 있음 | 66일차 정상 | 마지막 인증 |
| 10/22 04:00~16:00:00.000, 66일차 비어 있음 | 66일차 늦은 인증 | ‘마지막 날 늦은 인증’ |
| 위 시간에 66일차 이미 채움 | 쓰기 불가 | 기록 보기, 결과는 최종 집계 전 |
| 10/22 16:00:00.001 이후 | ENDED | 기록·확정 결과 보기 |

현재 `resolveCheckinTarget`은 04:00부터 late=true지만 `isLate`는 createdAt > deadline여서 정확히 04:00에는 분류가 다르다. **신규 계약 제안은 정상 창 t < deadline, 늦은 창 deadline ≤ t ≤ lateWindowEnd로 통일**한다. 구현 시 이 경계 변경을 명시하고 회귀 사례를 추가해야 한다. 기존 정책 코드에는 아직 반영하지 않았다.

늦은 인증 가능 판정은 [time.ts](../sixtysix-v2/src/domain/selectors/time.ts)와 [checkinGate.test.ts](../sixtysix-v2/src/domain/__tests__/checkinGate.test.ts)에 이미 있다. D06은 재선택할 정책이 아니라 홈과 쓰기의 불일치를 바로잡을 기준이다.

### 4.3 홈 상태와 다음 행동

| 상황 | 표시 | 우선 행동 |
|---|---|---|
| 비참여 | 참여할 코호트 없음 | 모집 목록 |
| 참여 확정·시작 전 | 시작 대기 | 시작일 안내 / 참여 취소 |
| 오늘 비어 있고 어제도 비었으며 늦은 창 열림 | 기존 broken/dormant + 어제 접수 안내 | 어제 대상 인증 |
| 오늘 비어 있고 오늘 접수 가능 | ongoing/broken/dormant | 오늘 인증 / 면제권 |
| 오늘 인증 있음 | done + checkin | 코호트 피드 / 내 기록 |
| 오늘 면제권 있음 | done + pass | ‘면제권으로 채웠어요’, 기록 보기 |
| 끊긴 뒤 오늘 인증 성공 | done + returning | 복귀 완료 / 내 기록 |
| 일정 종료, 마지막 접수 가능 | ended + finalLateAvailable | 마지막 날 늦은 인증 |
| 일정 종료, 접수 불가 | ended | 기록 보기. serverNow > finalSubmissionAt일 때 결과 확정 |

`returning`은 별도 저장 상태로 만들지 않는다. 어제의 늦은 인증을 먼저 남긴 직후에는 오늘이 여전히 비어 있을 수 있으므로 자동으로 ‘오늘 인증 완료’를 띄우지 않는다.

최종 집계 이전 결과에는 `isFinal=false`와 `finalSubmissionAt`을 포함한다. 정확히 최종 접수 시각까지는 허용하므로 `serverNow > finalSubmissionAt`일 때 확정한다. 다음 코호트의 시작은 현재 코호트 최종 접수 종료 이후로 잡아 두 코호트의 쓰기 기간이 겹치지 않게 한다.

## 5. 데이터 계약

| 테이블/책임 | 제약과 저장 내용 |
|---|---|
| users / profiles | 서버 ID, 이름, 계정 상태. 이메일을 공개 응답에 싣지 않음 |
| auth_identities | userId, provider=email/kakao, providerSubject. UNIQUE(provider, providerSubject). 이메일 로그인 주소 검증과 카카오 사용자 ID를 각각 소유권 근거로 사용 |
| auth_challenges / link_intents | 만료·일회성 인증 시도 및 연결 목적, 현재 사용자·브라우저 세션에 바인딩. 코드 원문 저장 금지 |
| habits / policy_versions | 카탈로그, 불변 정책 버전. 코호트 생성 후 정책 내용을 덮어쓰지 않음 |
| cohorts | habitId, 모집 기간, startDate, 정원, 정책 버전, 취소 사실. 기수·ID는 서버 생성 |
| memberships | userId, cohortId, joinedAt, cancelledAt. 같은 사용자·코호트는 한 행으로 관리하고 재참여는 시작 전 취소 상태에서만 허용 |
| user_cohort_slots | userId UNIQUE, 현재 참여/시작 대기 membershipId. 참여 명령에서 종료된 슬롯을 정리하고 점유 |
| day_entries | membershipId, cohortDay, kind=checkin/pass, createdAt. 두 ID와 일차는 NOT NULL, UNIQUE(membershipId, cohortDay) |
| checkin payload | 첫 단계는 day_entries에 text, samplePhotoRef?, visibility 포함. pass 행에서는 이 세 필드를 null로 제한 |
| preferences | 공개 기본값. 과거 인증 visibility와 독립 |
| idempotency_records | userId + 명령 범위 + key UNIQUE, 정규화 요청 hash, 원래 응답, 처리 상태 |
| 운영 감사 기록 | 참여 취소·노출 중단·권한 변경·중요 쓰기 추적. 인증번호·세션·인증 본문은 로그에 기록하지 않음 |
| reports / support_requests | 신고·문의, 신고자, 대상, 처리 상태·운영자 조치. 일반 회원은 타인의 요청 열람 불가 |
| deletion_requests / outbox | 탈퇴 처리 상태·실패 재시도, 모집 취소·처리 결과 안내 이벤트. 알림 발송과 핵심 DB 변경을 분리 |

`DayEntry`는 앞 문서의 Checkin/PassUsage를 API에서 그대로 표현할 수 있게 하는 DB 내부 구조다. 코호트 일차 범위는 해당 정책과 함께 서버에서 검사하고, 첫 정책의 1~66 제한은 DB에서도 보조한다.

시간에 따라 변하는 ‘진행 중’ 상태를 단순 인덱스 조건으로 삼지 않는다. 사용자 슬롯과 트랜잭션에서 참여 기간을 계산한다. 정원·면제권 총횟수 역시 행 하나의 CHECK만으로 보장할 수 없다. UNIQUE·NOT NULL과 행 단위 CHECK의 역할은 [PostgreSQL 제약 문서](https://www.postgresql.org/docs/current/ddl-constraints.html)를 참고했다. T02 개발 기준은 PostgreSQL이며 관리형 공급자는 미선정이다.

### 명령의 원자성

- 참여: 사용자 잠금 → 코호트 잠금 → 시작/모집/정원/슬롯 재검사 → 멤버십·슬롯 저장. 참여 취소도 같은 잠금 순서.
- 인증·면제권: 인증된 소유자 확인 → 멱등 요청 확인 → 멤버십 잠금 → 시간·대상 일차·중복·면제권 횟수 재검사 → 사실·멱등 응답을 같은 트랜잭션에 저장.
- 이미 성공한 같은 키/입력의 재시도는 시간이 넘어가도 원래 성공 결과 반환. 다른 입력으로 같은 키를 쓰면 충돌.
- 사용자가 다른 키로 같은 날 다시 보내면 ALREADY_FILLED. 서로 다른 날짜 면제권도 멤버십 잠금으로 총횟수 제한.
- 성공 키는 최소 코호트 최종 접수 종료까지 보존하고 세부 보존 기간은 운영 설정으로 명시. 기록 정리 후에도 일차 UNIQUE는 중복 생성을 막는다.

## 6. API 초안 v0.1

모든 업무 API는 세션 기준이다. 경로의 membershipId는 권한 검사를 통과해야 한다. 아래는 구현 전 계약이며 인증 공급자와 호스팅 선택 후 세션 전달 방식 세부를 고정한다.

운영 API는 일반 회원 API와 권한을 분리한다. 모집 개설/취소, 신고 처리, 노출 중단, 탈퇴 작업 재시도 명령에 운영자 인증·감사 기록을 적용한다. 구체 경로는 OpenAPI v0.2에 작성했다. 보관 기간은 운영 정책 미결 항목이다. CSRF 문맥·기존 수단 재인증·카탈로그·본인 신고/문의 조회도 OpenAPI에 추가했다.

인증 요청 예시:

```json
{
  "text": "오늘도 15분 읽었어요",
  "samplePhotoRef": null,
  "visibility": "cohort",
  "expectedTargetDay": 23,
  "expectedLate": false
}
```

허용하지 않는 입력: 소유자 userId, createdAt, 확정 cohortDay, 점수, 연속 기록. unknown field는 조용히 적용하지 않고 입력 오류로 처리한다.

문자 제한은 우선 기존 JS `trim().length`와 같은 UTF-16 코드 단위 1~40으로 맞춘다. 사용자 인식 글자 수로 바꾸려면 UI·서버·정책을 함께 변경한다. samplePhotoRef는 서버 카탈로그 허용 목록만 받는다.

홈의 쓰기 가능 응답 예시:

```json
{
  "serverNow": "2026-09-08T08:00:00.000Z",
  "policyVersion": 1,
  "cohortDay": 23,
  "displayDay": 23,
  "state": "broken",
  "todayStatus": "empty",
  "availability": {
    "ok": true,
    "targetDay": 23,
    "late": false,
    "targetDate": "2026-09-08"
  },
  "action": { "type": "CHECKIN", "label": "오늘 인증 남기기" }
}
```

위 JSON은 홈 전체 응답 중 판정 필드의 예시이며 전체 schema는 아니다. progress·participation·passesLeft는 같은 serverNow와 일관된 DB 읽기에서 계산한다. 클라이언트는 action.type을 경로에 매핑하고 서버의 임의 URL을 실행하지 않는다.

폼을 연 뒤 targetDay **또는 late 여부**가 바뀌면 409 TARGET_CHANGED와 새 availability를 반환한다. 입력은 보존하고 날짜·정상/늦은 분류를 다시 확인한 뒤 **새 요청 키**로 보낸다. 동일 요청의 네트워크 재시도에는 원래 키를 사용한다.

피드 limit 기본 20/최대 50 제안. createdAt DESC, id DESC의 안정된 커서를 사용한다. 비공개 전환 직후부터 후속 조회와 직접 접근에 반영한다. 이미 다른 사용자 브라우저에 표시된 콘텐츠를 소급해 회수할 수 있다고 약속하지 않는다.

## 7. 오류와 UI 대응

공통 형태: `{ error: { code, message, requestId, details? } }`. 사용자에게 DB 내부 오류나 다른 사용자의 기록 존재 여부를 노출하지 않는다.

| HTTP | code | UI 처리 |
|---|---|---|
| 400 | INVALID_REQUEST / INVALID_TEXT / INVALID_MEDIA | 입력 유지, 해당 필드 안내 |
| 401 | UNAUTHENTICATED | 로그인으로 이동. 작성 초안 보존 여부는 기기 내 정책에 맞춤 |
| 404 | NOT_FOUND | 없거나 접근 불가한 업무 리소스는 동일 안내 |
| 409 | COHORT_FULL / JOIN_CLOSED / ACTIVE_MEMBERSHIP_EXISTS | 최신 모집/참여 상태 조회 |
| 409 | ALREADY_FILLED | 최신 기록으로 이동. 중복 성공으로 꾸미지 않음 |
| 409 | PASS_EXHAUSTED | 남은 횟수 갱신, 인증 동선 제공 |
| 409 | BEFORE_START / ENDED | 시작 대기 또는 기록 화면 |
| 409 | TARGET_CHANGED | 날짜·늦은 여부 확인 후 새 키로 접수 |
| 409 | IDEMPOTENCY_CONFLICT | 다른 입력으로 키 재사용. 자동 재시도 금지 |
| 409 | IDENTITY_ALREADY_LINKED / LAST_IDENTITY | 다른 계정 소유 수단 연결 또는 마지막 로그인 수단 해제를 막음 |
| 429 | RATE_LIMITED | Retry-After에 따라 대기 안내 |
| 503 | TEMPORARILY_UNAVAILABLE | 입력 유지, 재시도 제공. 같은 쓰기는 같은 키 |

인증번호 만료·오류는 사용자 존재 여부를 구분하지 않는 실패 안내를 사용한다. 시도·발송 빈도 제한은 공급자와 API 양쪽의 책임을 확인한다. 이 방향은 [OWASP 인증 지침](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)의 일반 오류·시도 제한 원칙을 따른다.

## 8. 인증과 권한의 첫 계약

이메일은 코드 발송 → 코드 검증 → 최초 프로필 입력 → 코호트 목록 순서다. 카카오는 인가 요청 → 서버 콜백 검증 → 사용자 ID 확인 → 서비스 계정 조회/생성 → 같은 코호트 목록으로 연결한다. 두 수단의 로그아웃은 서비스 세션을 폐기하는 동작이며, 카카오 계정 자체 로그아웃·서비스 연결 해제와 구분한다.

카카오 인가 코드·토큰 교환, 등록된 redirect URI, 요청별 state 검증은 [카카오 공식 REST API 문서](https://developers.kakao.com/docs/ko/kakaologin/rest-api)를 기준으로 구현한다. 앱·redirect URI·동의 항목은 [사전 설정 문서](https://developers.kakao.com/docs/en/kakaologin/prerequisite)에 맞춰 준비한다. 카카오 이메일을 받을 수 있다고 전제하지 않고 provider 사용자 ID를 식별자로 쓴다.

**계정 연결 권장 계약:** 로그인된 계정을 최근 재인증하고 새 수단의 소유권도 별도로 검증한 뒤 같은 userId에 연결한다. 카카오 프로필 이메일과 이메일 로그인 주소가 같아도 자동 병합하지 않는다. 다른 서비스 계정에 이미 연결된 수단은 IDENTITY_ALREADY_LINKED로 막고 기존 계정 로그인 안내를 제공한다. 두 계정의 기록을 자동 병합하는 기능은 제외한다. 새 계정 생성 화면에 기존 계정으로 로그인해 연결하는 동선을 둔다.

연결 해제는 다른 유효 로그인 수단이 남아 있을 때만 가능하다. 이메일 접근을 잃었더라도 연결된 카카오로 로그인·재인증할 수 있게 한다. 모든 수단을 잃은 경우에는 별도 본인 확인 절차 없이 운영자가 소유권을 넘기지 않는다. 연결 intent는 현재 사용자·목적·세션·만료에 묶고 한 번만 소비하며, 연결 콜백이 일반 로그인으로 다른 계정을 바꾸지 않도록 분리한다.

인증 코드 수명·발송 재시도·입력 횟수는 공급자 선택 때 환경 설정값과 사용자 문구를 함께 고정한다. 첫 구현 수용 기준에 만료·재사용·과도한 요청·잘못된 코드 차단을 포함한다.

웹 세션은 HttpOnly·Secure 쿠키를 우선 검토하고, 변경 요청의 CSRF 방어와 허용 Origin을 함께 설계한다. 로그인/로그아웃·세션 회수·만료 정책을 테스트한다. [OWASP 세션 지침](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)을 구현 검토 기준으로 사용한다. 프런트와 API의 실제 도메인 배치가 정해지기 전 SameSite·CORS 구성을 임의 확정하지 않는다.

본인 기록은 본인만, 코호트 공개 인증은 해당 코호트의 취소·이탈되지 않은 참여자만 볼 수 있다. 시작 대기 구성원 명단은 시작 후 공개하는 안을 제안한다. 비회원에게는 습관·일정·현재 모집 인원만 공개한다.

공개 출시 전에는 셀프 탈퇴와 중도 이탈 UI를 제공한다. 계정 탈퇴 요청은 모든 서비스 세션을 회수하고 인증 수단과 공개 기록 접근을 즉시 차단한 뒤 삭제 작업을 수행한다. 중도 이탈은 해당 코호트의 쓰기·타인 피드 열람을 종료하며 본인 기록은 보관하는 안이다. 무분별한 갈아타기를 막기 위해 원래 코호트 최종 접수 종료까지 신규 참여 슬롯을 유지하는 안을 제안한다. 이탈자 식별 정보는 순위에서 제외하고 집계의 익명 처리·보관 기간·삭제 완료 기한은 오픈 전 운영 명세에서 확정한다.

모집은 시작 시 코호트 잠금 하에서 최종 인원을 확인해 started/cancelled 결정을 한 번 저장한다. 최소 인원 미달은 다른 코호트로 자동 이동시키지 않고 취소 결과와 다시 선택할 동선을 제공한다. 배치 처리가 늦어져도 첫 조회/쓰기 전에 시작 판정을 실행해 잘못 인증을 받지 않는다. 모집 인원·참여율의 분모는 실제 참여 인원이며 정원 30과 구분한다.

T02의 기술 기준안·업무 migration·OpenAPI는 작성하고 로컬 검증했다. 인증 공급자 최종 고정은 T03a 호환성 검증 후 진행한다. 서버 골격·인증 테이블 생성·실제 로그인·환경 배포는 다음 구현 작업이며 T02 전체 기반이 기동되는 상태는 아니다.
